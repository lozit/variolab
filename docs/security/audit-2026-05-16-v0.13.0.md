# Security Audit Report — `variolab` v0.13.0

**Date** : 2026-05-16
**Branch** : `main` @ `31fdb8e`
**Auditor** : situated + OWASP grid (skill `/security-audit`)
**Previous** : [`audit-2026-05-03-v0.12.0.md`](./audit-2026-05-03-v0.12.0.md)

> v0.13.0 is the **second trademark rename** (`Uplift – A/B Testing` → `Variolab – A/B Testing`, slug `uplift-ab-testing` → `variolab`) following wp.org Plugin Review Team feedback. "Uplift" was flagged on two cumulative grounds: (1) non-distinctive — it's the standard industry term for the A/B-testing lift metric; (2) UPLIFT® is a live USPTO trademark (Reg. 4973441, UPLIFT INC., San Francisco) in the same "Advertising, Business & Retail Services" class. "Variolab" is an invented term (vario + lab) with 0 hits on wp.org / USPTO / SaaS at name-pick time.
>
> Unlike v0.12.0 (pure cosmetic rename, carry-forward audit), v0.13.0 contains **real security work** addressing the wp.org reviewer findings: 9 `$_SERVER` reads now sanitized at intake, the cache-bypass admin notice goes through `wp_kses` with an explicit allowlist, and the per-URL tracking-script save handler is gated by the `unfiltered_html` capability (WP-canonical gate for users who can input raw HTML/JS). Each fix is reviewed below.
>
> **Internal naming deliberately preserved** (security-relevant — a rename here would invalidate the audit baseline AND break existing installs): PHP namespace `Abtest\`, hook prefixes `abtest_*`, cookies, REST namespace `abtest/v1`, custom table `wp_abtest_events`, option keys, `visitor_hash` salting, HMAC webhook signing, consent gate.

## Step 2 — Situated checklist (per-surface)

### A. `admin_post_*` handlers — ✅
All 8 handlers verify `current_user_can('manage_options')` **and** `check_admin_referer(...)` before any mutation. Verified:

| Handler | File:line | Cap check | Nonce check |
|---|---|---|---|
| `handle_save` (experiment edit) | `Admin/Admin.php:176` | ✅ L177 | ✅ L180 (`self::NONCE`) |
| `handle_status_change` | `Admin/Admin.php:358` | ✅ | ✅ `abtest_status_change` |
| `handle_replace_running` | `Admin/Admin.php` | ✅ | ✅ `abtest_replace_running` |
| `handle_resume` | `Admin/Admin.php` | ✅ | ✅ `abtest_resume` |
| `handle_delete` | `Admin/Admin.php` | ✅ | ✅ `abtest_delete_experiment` |
| `handle_save` (settings) | `Admin/Settings.php:243` | ✅ | ✅ `abtest_save_settings` |
| `handle_test_webhook` | `Admin/Settings.php:293` | ✅ L294 | ✅ L297 (`abtest_test_webhook`) |
| `handle_upload` (HTML import) | `Admin/HtmlImport.php:207` | ✅ | ✅ `self::NONCE` |
| `handle_scan_now` | `Admin/HtmlImport.php:171` | ✅ | ✅ `self::SCAN_NONCE` |

Inputs pass through `wp_unslash()` then sanitize (`sanitize_text_field` / `absint` / `sanitize_key` / `esc_url_raw`). Redirects use `wp_safe_redirect()` everywhere.

**v0.13.0 delta** — `handle_save` adds a `current_user_can('unfiltered_html')` gate around the `$_POST['url_scripts']` persistence (Admin.php:331). Rationale documented inline:

> Trust model: scripts are admin-curated raw JS/HTML (Adwords pixels, FB pixels, Lemlist beacons). The `unfiltered_html` capability is the WP-canonical gate for users who can input raw HTML/JS (same gate used by the Custom HTML widget and the post editor's "Custom HTML" block). Single-site admins have it by default; multisite admins only get it explicitly granted by super-admins (correct behavior: don't let a tenant admin inject a pixel that fires on another tenant's traffic).

This is **strictly tighter** than v0.12.0 (which only required `manage_options`). No regression risk on single-site installs.

### B. REST endpoints — ✅

| Endpoint | File | permission_callback | Sanitize / dedup / rate-limit |
|---|---|---|---|
| `POST /abtest/v1/convert` | `Rest/ConvertController.php` | `__return_true` (intentional public — conversion tracking) | dedup by visitor_hash + 60 conv/min/IP transient rate-limit (filterable via `abtest_convert_rate_limit_per_min`) |
| `GET /abtest/v1/stats` | `Rest/StatsController.php` | `[$this, 'check_permission']` → `current_user_can('manage_options')` | args schema with validate_callback + sanitize_callback per param |

Responses don't leak secrets: visitor hashes are truncated to 16 hex chars (64 bits) at storage; no raw IP, no UA, no WP user ID returned.

**v0.13.0 delta** — `ConvertController::is_rate_limited()` now sanitizes `$_SERVER['REMOTE_ADDR']` (line 102). The IP value is then fed to `wp_hash()` for the transient key — never stored or echoed, but explicit sanitization is the reviewer's expected mitigation.

### D. SQL — ✅
Files: `Stats.php`, `Tracker.php`, `Experiment.php`, `Schema.php`, `Plugin.php`, `Admin/CsvExport.php`.

Every `$wpdb->get_results / get_var / get_col / query / prepare` call inspected:

- ✅ All user-input-derived queries use `$wpdb->prepare()` with proper placeholders (`%d`, `%s`).
- ✅ `IN (?)` clauses (Stats batched query) built from `(int)`-cast experiment IDs only.
- ✅ Plugin-controlled interpolation (`$wpdb->prefix . 'abtest_events'` via `Schema::events_table()`) carries explicit `phpcs:disable WordPress.DB.PreparedSQL.*` with rationale.
- ✅ Migration `pre_install_truncate_visitor_hash()` (Plugin.php:96-105) is idempotent (SUBSTRING on a 16-char value returns itself).

No regression.

### E. Cookies + hashing — ✅
File: `Cookie.php`.

- ✅ Cookie flags: `secure: is_ssl()`, `httponly: true`, `samesite: 'Lax'`, TTL ≤ 30 days (configurable via `abtest_settings.cookie_days`).
- ✅ `visitor_hash` salted with `wp_salt('auth')`, truncated to `HASH_LENGTH=16` (64 bits) at runtime AND in schema (`CHAR(16)` since v1.3.0).
- ✅ Webhook HMAC documentation recommends `hash_equals()` (timing-safe comparison) for the receiver.

**v0.13.0 delta** — `Cookie::visitor_hash()` now sanitizes `$_SERVER['REMOTE_ADDR']` and `$_SERVER['HTTP_USER_AGENT']` (line 83-87) before feeding them to sha256. Defense-in-depth — the values were already fed into a hash, never echoed — but the reviewer's expected pattern is now applied.

- ✅ Webhook HMAC secret never exposed in REST responses.

No regression.
